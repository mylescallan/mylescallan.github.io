Canvas: A New Child Of The DOM

Introduction

Games are created by Javascript in HTML5 by using the <Canvas> Object. Below is a Canvas, move your mouse over it (click to reset):

<Canvas>, like <h1>, <ul>, ..., etc, is a child of the DOM.

You can give <Canvas> an id and class, and, as an element of the DOM, it is an Object of the Document. Here is a small <Canvas>, which I have given the id "myCanvas", which I will use to develop the basic concepts that you will need to know:

Objects have Properties and Methods (values and functions) built in. It is the Methods built into <Canvas> that make it suitable for building games.

Understanding how to build games with Javascript in HTML5 is equivalent to understanding how to use Objects. So, for most of this overview, I will be focusing on explaining Objects.

Objects: Properties and Methods

Objects: The Straightforward Part

Creating your own Object is straightforward, and it is the first thing that you do (in Javascript) when you create a game (see ref. pp. ). 

// Create a Game Object
var Game = {
	canvas : undefined,
	canvasContext : undefined,
	rectanglePosition : 0,
	aMethod: function (parameter) {
		do stuff;
    }
};

This is the Object Literal way of creating an Object. Simply put, you create the Properties of the Object by literally writing out the "name:value" pairs.

As above, you can store variables in the Object, which are called Properties. Also, you can also write functions and store them in the Object, which are called Methods of the Object (which, as above, you do by simply naming a function within the code block when creating an Object).

Side note: As will be explained later, there is a related concept called Classes. These are generic Objects; that is, a general Class of Objects that you intend to use to create Objects from. You create Classes (or Constructors) by using slightly different notation, but the approach is the same. Like so: 

// Create an Object Class
var SomeObject = function() {
	var privateMember = "I am a private member";
	this.publicMember = "I am a public member";
	this.publicMethod = function() {
		console.log(privateMember, this.publicMember);
    };
};
newObject = new SomeObject();
AnotherNewObject = new SomeObject();

Side note, cont.: The last two statements create static Objects from the Class "SomeObject." So, you see, you can create as many Objects from this Constructor as you wish.

The DOM, as its name suggests, is replete with Objects. Javascript is an Object-oriented language and comes with its own store of Objects. Knowing what Objects are available, nevermind knowing what Properties and Methods are associated with those Objects, only comes with experience. There are too many Objects to learn straight off, and each of those Objects have Properties and Methods to learn ... which will surely fry your brain.

Objects: The "My Brain Hurts" Part

That part is straightforward: There are Objects available to you, they have Properties and Methods, and you will learn them (and learn which are best to use in various contexts) over time.

By "straightforward" here I mean linear and logical.

What is not straightforward, i.e. is nonlinear, is that you can (and will) make the Methods and Properties of the pre-created Objects, of the DOM and Javascript, Methods and Properties of your Game Object. For example, you are going to exploit the Methods of the <Canvas> Object to draw (and redraw) your game. Once you make your <Canvas> Object part of your Game Object, the Game Object inherits the Methods and properites of <Canvas>. And that, literally, is the only potential source of confusion (i.e. there will be so many inherited Methods (some of which will be inherited from other inherited Methods) and Properties that it will be difficult to keep track).

Below is a perfect example of what I am talking about. In this example, we create a Method for the Object "Game" called "Game.start" (that is (a) we create a function and (b) associate this function with the Game Object simply by giving the function the name "Game.something" - the "Object.Method" naming will now, and forever more, associate the new function with the Object as a Method of that Object). 

// Create a Game Method called "start"
Game.start = function() {
	Game.canvas = document.getElementById("myCanvas");
	Game.canvasContext = Game.canvas.getContext("2d");
	Game.mainLoop();
};

But the example that I use above does more. Inside the new Method that we have created for our Game Object, Game.start, we create/inherit other Methods for our Game Object: 

  • Game.canvas = document.getElementById("myCanvas");
  • Game.canvasContext = Game.canvas.getContext("2d");

At the start, I mentioned that I had given my <Canvas> Object the id "myCanvas". We can see that the "Game.start" Method creates a "Game.canvas" Method which is simply the <Canvas> that I created. And so "Game.canvas" now inherits all of the Properties and Methods of the HTML5 <Canvas> Object.

In fact, the next line exploits this: In the next statement, we see that there is a reference to the "canvas.getContext()" Method, a default Method of the <Canvas> Object of the DOM. Canvas displays images in what is called a context. A context is just the name used in HTML for the drawing surface that the images are rendered on. So now, this new Method that we have created (Game.start) is in fact, in part, a way to allow our Game Object to inherit the canvas.getContext() Method.

Here it is again, go through each line and note how we inherit Methods (initially it may appear to be a little circular - inside a Method we are creating, we are creating other Methods ... and those other Methods inherit properties from pre-created Objects - but it will become second nature very quickly): 

// Create a Game Method called "start"
Game.start = function() {
	Game.canvas = document.getElementById("myCanvas");
	Game.canvasContext = Game.canvas.getContext("2d");
	Game.mainLoop();
};

Objects By Any Other Name: Types

"Type" is the generic name given to "strings", "integers", "arrays", ... etc. What is important here is that (a) they have Properties and Methods, and so behave like Objects, and (b) there is an Image Type that we use to import graphics for our game. The Properties of the Image Type include i) source (src), ii) position, ... amongst others, and there are Methods that allow us to do interesting things with our images. As games are "image-heavy", we can use this Type/Object in our Game Object to do some of the heavy lifting (by getting our Game Object to inherit the Properties and Methods of the Image Type).

Side note: 1) Image Types are called simply by: 

Game.gameImage = new Image();

Which gives you access to a Method to set the source of this image. Once you set the source, the browser automatically begins loading the file and fills in the data for the width and height variables (which it extracts from the source file, which saves you having to specify that information): 

Game.gameImage.src = "../images/gameImage1.jpg";

2) Images in games are typically referred to as 'sprites'.
3) As images take time to load, it is advisable to set a wait time, or write code whose only job is to tell your program that all of the "game's assets" have loaded. More on that later.

Games

Overview

Games themselves are simple concepts. If we storyboard any game we will always come up with two simple concepts: draw and update. That is, we need to be able to display (draw) all of the aspect of the game (including the game background, features, characters, scores, etc). And, we need to be able to update all of those features (and also to update other features that may not be visible (score history, levels that we have attained, etc)). Obviously, draw and update have to be linked (as any update - a player action like moving the mouse, for example - has to be drawn). So we draw and update the game features in a "main loop". These are the three features of any game: draw, update, main loop.

Simple! The only complicated part is 'how do we avail ourselves of the Objects in the DOM and Javascript to facilitate the elements of our game?' (for example, cursor position, buttons pressed, changes in images (to signify a 'hit' for example)). It turns out that the DOM and Javascript, together, have more than enough features to create any game that you can imagine ... including in 3d.

Here is how we begin: We create the mainLoop Method for our Game Object and in it we include the update and draw Methods, so that they occur in the same time frame. And finally, we use a Method from the DOM to update our Game every so often (specified in milliseconds). 

// Create a Game Method called "mainLoop"
Game.mainLoop = function() {
	Game.clearCanvas();
	Game.update();
	Game.draw();
	window.setTimeout(Game.mainLoop, 1000 / 60); // refreshes the page 60 times a second by reloading "mainLoop"
};

Side note: 1) We are using the mainLoop Method inside the specification of the mainLoop Method ... initially that may look odd (how can we use the mainLoop Method inside the place where we are defining the mainLoop Method?) but this is a pretty standard trick in programming called recursion. When you think about it, it is actually the most sensible place to ensure that mainLoop loops - read the code line-by-line and follow the instructions one step at a time, you'll see that you'll be in a loop that continues forever (alternatively, we could put the window.setTimeout in a loop (outside of the mainLoop Method code block) and there would be no difference in outcome (but it would be more of a pain to write)).
It is important here to elaborate on this point as the answer to the vital question: How does the Game update/refresh? is given by this one line of code, and this one line of code does this by recursion.

2) The Game.clearCanvas() Method does as its name suggests, it clears the canvas. In fact, it is clearing the canvas that gives the appearance of motion!! We clear and redraw the canvas 60 times a second, say, and it looks like things are moving ... which is identical to how movies work, the more (static) frames per second, the more realistic the movie appears. (Current TV standards are NTSC and PAL which have a 29.97 fps (frames per second) rate and a 25 fps rate, respectively. So 60 fps, as in the Game.mainLoop is more than sufficient to project realism.)

Tools (Methods) For Games Available in the DOM and Javascript.

Let's begin by listing some of the key Methods used in most games. This approach should prove useful because it - by listing just a few of the Methods of the DOM and Javascript used in a typical game - should: a) give you a sense of the possibilities, and b) make it easier to understand the various key Methods (as many, if not most, of the details of a Game program, while essential, are there simply to organize your code). As we have seen, the actual structure of a game is relatively simple but organizing each of the details (loading images and sounds ("assets" of the game), changing images and sounds in response to players actions ("events"), and so on) takes considerable organization. On first blush, in the midst of all of the code that organizes the game, you can miss the essential features that create the game.

  1. Define Your Game Object: A DOM Method 
    // Create a Game Object
var Game = {
	canvas : undefined,
	canvasContext : undefined,
	other parts : undefined
};
    We set up our game Object by simply defining the parts using the Object Literal approach. Once we have our basic game Object, we can, later, define Methods of the game.

  2. Define Your Game Methods: A DOM Method 
    Game.start, Game.draw, Game.update, & Game.mainLoop
    These are the 4 key components of any game. Where Game.start contains the basic building blocks, such as defining your canvas: Game.canvas = document.getElementById("myCanvas");.

  3. Motion: A DOM Method 
    window.setTimeout(Game.mainLoop, 1000 / 60);
    As we have seen, this refreshes the page 60 times a second by reloading the "mainLoop" Method by recursion.

  4. Draw Image (on screen) & Image Position: A DOM (<Canvas>) Method 
    Game.canvasContext.drawImage(gameImage, 0, 0 gameImage.width, gameImage.height, 0, 0, gameImage.width, gameImage.height);
    We saw earlier that we made our Game Object inherit the Canvas Object's getContext Method, which we called Game.canvasContext. drawImage is a Method that belongs to the canvas’s drawing surface (the 2D context), and our Game Object inherits this method. We see here that this Method, drawImage, allows us to a) draw the image, and b) set its position. (All positional data are set with a reference point that is the top left of the canvas (NOTE: not the screen), which is position 0, 0 (in terms of width and height, in that order)).
    drawImage Method takes nine parameters: The name that we gave the image followed by "0, 0 gameImage.width, gameImage.height" written twice.
    Think of the space occupied by the image as a rectangle. So the second set of positional data gives the image a space on canvas that begins at the top left of the canvas, with the rectangle dimensions given by the width and height of the image.
    The first reference to "0, 0 gameImage.width, gameImage.height" simply tells your browser how much of the image to draw. Here, we draw the full image. These first 4 co-ordinates are optional. If you omit them, the full image will draw.
    Order Matters! One of the images that you are going to draw is the background to your game. When you draw the background, you have to draw it before you draw all of the other images. Otherwise, you will be drawing your background over some of your other images.

    Side note: There are two vital point to note here, that help to clarify the use of Objects in building games (or simply writing Javascript):
    1) Inheritance: We are using a <Canvas> Object Method but we are calling a Game Object Method. Which we can do because of an earlier pair of instructions: 

    Game.canvas = document.getElementById("myCanvas");
Game.canvasContext = Game.canvas.getContext("2d");

    2) Conciseness: This one instruction embodies a whole host of inner instructions (that you don't have to write out because you are using Objects): We inherited the Methods of another Object; The Method that we inherited allows us to both draw the image and set its position; The use of the Image Type means that we didn't have to specify the image's width and height, we just use the Image.width and Image.height Methods, and so on. The only cost is that we now have all of those instructions in one statement, which requires the investment of time in learning which Objects exist and what Properties and Methods those Objects have.


  5. Image Motion: : A DOM (<Canvas>) Method
    Moving an image again uses one of the Methods of the (<Canvas>) Object, called "translate" (in the "getContext()" method). By ensuring that the Game Object has inherited these methods, we can use: 
    Game.canvasContext.translate(Game.gameImagePosition.x, Game.gameImagePosition.y);
    The Game.gameImagePosition.x and Game.gameImagePosition.y are the x, y co-ordinates of where we want to move/translate the image to. First we have to create these co-ordinates (at an initial position), which we do as part of the Game Object (using the Object Literal approach): 
    var Game = { ...
   gameImagePosition : {x : 0, y : 50},
                        ...
}
    Obviously, these coordinates are fixed, so how do we supply motion? One way is to use the Date Object (which is part of the DOM, and has a Method "getTime" that measures the time in milliseconds since the 1st of January 1970). As time is constantly moving forward, we can use this Date Object to generate constantly moving co-ordinates.
    Once we have generated these constantly moving co-ordinates, we can redraw the image in the "update" part of our game. So how do we do this? 
    var d = new Date();
Game.gameImagePosition.x = d.getTime() % Game.canvas.width;
    Firstly, we are only changing the "x" coordinate (so the image will move horizontally across the page). If we move both, by adding "Game.gameImagePosition.y = d.getTime() % Game.canvas.height;", then the image will move diagonally.
    Secondly, as the number of milliseconds since 01.01.1970 is a huge number (currently 1428514411081), that will be no use as a co-ordinate. So we use the modulus operator (%, which is built into Javascript). This gives us the remainder when our huge number is divided by the width of the canvas (this remainder has to be, by definition, somewhere between 0 and the width of the canvas). Now the image position, when updated, is constantly moving (as the remainder is constantly changing) - as you can see on the canvas below.


  6. Image Motion Based On An Event: : A DOM Method
    In the case above, the motion of the image was independent of events occuring in the game. Obviously, that has its uses in a game but we also need to be able to move images by keystrokes or mouse movements - otherwise it is not a game. Fortunately, this is a simple extension of what we did in the previous example. This time we are going to rely on elements of the DOM to record keystrokes or mouse movements and then use these to update the positions of our images. Again we use: 
    Game.canvasContext.translate(Game.gameImagePosition.x, Game.gameImagePosition.y);
    We intialize the image positions as before, but now we want to change the position of the image based on movements of the mouse. Fortunately, the DOM has a simple Method to do just this, called "document.onmousemove". 
    // Mouse position information. NOTE: We use clientX and client Y instead of pageX and pageY
// in case the canvas is on a part of the page that the user has to scroll too.
function getMousePos(evt) {
	               Game.mousePos = { x : evt.clientX, y : evt.clientY};
}
// For touchscreens: Finger position information
function getTouchPos(evt) {
	               Game.mousePos = {x : evt.clientX, y : evt.clientY};
	               evt.preventDefault(); // Allows for touch events in areas where there may be links
}                  

// Call the mouse/finger position event handlers, checking whether you are using a browser or iPhone or iPad in Game.start Object
if ((navigator.userAgent.match(/iPhone/i)) || (navigator.userAgent.match(/iPod/i))) {
	               Game.canvas.addEventListener('touchmove', getTouchpos);
} else {
	               Game.canvas.addEventListener('mousemove', getMousepos);
}

// Move the image with the mouse, used in the Game.draw Object
Game.gameImagePosition = {x: Game.mousePos.x, y: Game.mousePos.y};
    clientX and clientY are Methods (of the "event" Object stored in "Game.canvas.onmousemove") that return the x, y co-ordinates of the mouse's position. As before, we include "Game.gameImagePosition" in the "draw" Object which is updated in the "update" Object, but now the image will move with the position of the mouse. Which you can see if you move your mouse over the canvas below.
    There are similar methods for other events, such as key strokes. More on those later.

    Side note: Canvas Position:
    If your canvas is not positioned at {x : 0, y : 0}, i.e. the top left, of your document, then you have to adjust your mouse position to be relative to the canvas, and not the page as a whole. This is because all of the other positions within the game, image position, background position, etc, are relative to the canvas. Fortunately, this is simply done.

    function getMousePos(canvas, evt) {
	var rect = canvas.getBoundingClientRect();
	return {x : evt.clientX - rect.left, y : evt.clientY - rect.top};
}

    "getBounding" is a canvas Method that calculates the position of the canvas (and more besides). Scroll over the canvas below and you can see the difference between the pointer coordinates measured in pixels from the corner of the canvas and the corner of the document, respectively (watch how only one changes as you scroll up and down the page).
